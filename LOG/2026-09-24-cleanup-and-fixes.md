## 1. findContours가 같은 선을 두 번 그림

**정의.** 기존 코드는 Canny 엣지에 `findContours`를 적용해 나온 윤곽을 그대로 획으로 썼습니다. findContours는 "흰 영역의 경계"를 돌려주는 함수라서, 두께 1px인 선에서는 선을 따라갔다가 반대편 경계를 따라 되돌아오는 폐곡선이 나옵니다. 로봇은 같은 선을 두 번 긋게 되고, 그리는 시간도 두 배가 됩니다. 이전 결과 이미지(CV/experiments/sketch_step3_after.png) 오른쪽 패널에서 선이 이중으로 겹쳐 보이던 것도 이 때문입니다.

**재현.** 280px 길이의 1px 직선에서 findContours 윤곽의 길이는 559px, 점은 560개였습니다.

**해결.** `CV/sketch_pipeline.py`의 `trace_strokes()`
1. scikit-image `skeletonize`로 선을 1px 중심선으로 만든다.
2. 픽셀마다 8-이웃 수를 센다. 1이면 끝점, 3 이상이면 분기점이다.
3. 끝점이나 분기점에서 출발해 다음 끝점이나 분기점까지 따라간 경로를 획 하나로 만든다. 지나간 간선은 기록해 두어 두 번 지나가지 않는다.
4. 끝점도 분기점도 없는 고리(원 등)는 닫힌 획으로 따로 처리한다.

기존 방식은 `--method contour`로 계속 비교할 수 있습니다.

**검증.**
- 단위 테스트: 직선은 1획·280px, 원은 닫힌 1획, T자는 3획.
- 합성 그림(집, 창문, 문, 글자; `assets/2026-09-24-cleanup/synthetic_house.png`), medium 상세도, 100mm 상자 기준:

| 방식 | 획 | 점 | 펜다운 길이 | 이론상 최소 시간 |
|---|---|---|---|---|
| contour (기존) | 38 | 344 | 2183.6 mm | 467 s |
| skeleton + Canny | 23 | 170 | 1088.5 mm | 246 s |
| skeleton + dark (선화 모드) | 28 | 96 | 587.7 mm | 138 s |

"이론상 최소 시간"은 펜다운 길이 ÷ 300 mm/min + 펜업 거리 ÷ 600 mm/min만 계산한 값입니다. 명령 처리 지연과 가감속은 빠져 있으므로, 실제 실행 시간과 비교해 보정해야 합니다.

비교 이미지: `assets/2026-09-24-cleanup/contour_preview.png`, `skeleton_canny_preview.png`, `skeleton_dark_preview.png`. 네 칸 구성은 입력 / 선 후보 / 획 / 그리는 순서(파랑→빨강, 회색 점선 = 펜업 이동)입니다.

## 2. Canny가 굵은 선을 두 줄로 만듦

**정의.** Canny는 밝기가 바뀌는 곳을 찾기 때문에, 두께가 있는 검은 선에서는 왼쪽 경계와 오른쪽 경계가 각각 선으로 나옵니다. 1번을 해결해도 이 두 줄은 그대로 남습니다(skeleton_canny_preview.png의 집 외곽선).

**해결.** `compute_dark_mask()`와 `--lines dark` 옵션을 추가했습니다. Otsu 이진화로 어두운 선 영역 자체를 고른 뒤 골격화하면 선의 중심선 한 줄을 얻습니다.

**검증.** 두께 6px 직선에서 Canny는 합계 450px 이상(두 줄), dark 모드는 290px 미만(한 줄)입니다(단위 테스트).

**한계.** 사진처럼 선이 아닌 명암으로 된 입력에는 Canny가 여전히 기본입니다. 채워진 면(합성 그림의 검은 원)은 dark 모드에서 거의 사라집니다. 면을 해칭으로 채우는 기능은 이번 범위가 아닙니다.

## 3. 조각 단위 길이 필터가 글자를 지움 (작업 중 발견)

**정의.** 1번의 추적 방식은 분기점마다 획을 나눕니다. 여기에 기존처럼 "획 하나의 길이 < 15px면 버림" 필터를 적용하자, 글자처럼 분기점이 많은 선이 잘게 쪼개진 뒤 통째로 사라졌습니다. 합성 그림의 "MIROBOT"이 "~IPOBOT"처럼 나왔습니다(`dark_before_filter_fix_preview.png`).

**해결.** 필터를 두 단계로 나눴습니다.
- 잡음 제거는 "서로 이어진 선 덩어리" 전체의 픽셀 수 기준으로 한다(connectedComponents).
- 골격화 부작용인 짧은 잔가지만 따로 제거한다. 한쪽 끝은 허공이고 다른 끝은 분기점이며, 길이가 6px 미만인 조각이 대상이다.

**검증.** 글자 이미지에서 원래 글자 영역을 덮는 비율:

| 방식 | 덮는 비율 |
|---|---|
| 필터 없음 (상한) | 0.915 |
| 조각 단위 필터 (수정 전) | 0.661 |
| 덩어리 단위 필터 (수정 후) | 0.894 |

떨어진 점 잡음은 계속 제거됩니다(단위 테스트).

## 4. 픽셀 → 종이 mm 변환

**정의.** GUI는 픽셀 좌표 JSON만 저장했고, 안내 문구가 가리키던 `sketch_step4.py`는 존재하지 않았습니다. 이미지 y축은 아래로 갈수록 커지고 종이 위쪽은 +여야 하므로, 변환할 때 부호를 뒤집어야 합니다.

**해결.** `CV/paper_mapping.py`
- 획 전체의 경계 상자 중심을 종이 중심에 맞춘다(설계 5.2).
- 가로세로 비율을 유지하면서 그리기 상자 안에 넣는다. 기본 상자는 100×100mm다.
- 출력은 `sketch_strokes` JSON이다. 좌표는 종이 정면 기준 x 오른쪽 +, y 위쪽 +이고 단위는 mm다. 사용한 파라미터와 지표도 함께 저장한다.

로봇 축으로의 변환은 일부러 실행기 쪽에 두었습니다. 로봇 설정이 바뀌어도 CV 결과를 다시 만들 필요가 없게 하기 위해서입니다.

**검증.** 200×100px 사각형이 100×50mm로 바뀌고, 중심이 원점에 오며, 위쪽 변이 +25mm가 되는지 확인했습니다. 종이보다 큰 상자는 거부됩니다(단위 테스트).

## 5. 획 순서 최적화

**해결.** `order_strokes()`는 펜의 현재 위치에서 가장 가까운 시작점을 가진 획을 다음 획으로 고릅니다(탐욕 최근접). 열린 획은 가까운 쪽 끝에서 시작하도록 뒤집을 수 있고, 닫힌 획은 가장 가까운 꼭짓점에서 시작하도록 시작점을 돌립니다.

**검증.** 무작위 획 30개에서 펜업 이동 거리가 정렬 전의 60% 미만으로 줄었습니다(단위 테스트).

## 6. 로봇 실행기

**정의.** 설계 문서는 "MoveIt 관절 궤적 JSON → Windows 실행기"를 가정했습니다. 그러나 실제로 끝까지 실행된 원·하트 테스트는 컨트롤러의 Cartesian 직선 이동을 썼고, 그 실행 코드는 폴더에 없었습니다. `mirobot_control.py`에는 관절 이동과 그리퍼·펌프 기능만 있습니다.

**결정.** 1차 실행 경로는 실물에서 확인된 Cartesian 방식으로 합니다. MoveIt은 RViz 검토용으로 유지합니다(설계 문서 12절). 도달 범위나 특이점 문제가 생기면 관절 궤적 방식을 다시 평가합니다.

**해결.** `robot/draw_executor.py` + `robot/drawing_config.json`
- 명령 형식은 `M20 G90 G01 X Y Z A B C F`(절대 좌표)입니다. 테스트 때 쓴 상대 좌표(`G91`)는 오차가 누적될 수 있어 절대 좌표로 바꿨습니다.
- 명령 순서: 종이 중심 펜업 → 각 획마다 [펜업 이동 → 펜다운 → 그리기 → 펜업] → 중심 복귀.
- 펜업은 접촉 위치에서 -X 방향으로 2.5mm 후퇴합니다. 테스트 기록(접근 전 X=196.678, 접촉 X=198.668)을 근거로 했습니다.
- 평면 보정식 `X = cx + a·dY + b·dZ` 자리를 만들어 두었습니다. 현재 a=b=0이며 측정 후 채웁니다.
- 기본은 dry-run입니다. `--execute`를 붙였을 때만 시리얼 포트를 엽니다.
- 안전 검사:
  - Idle이 아니면 시작하지 않는다.
  - 현재 TCP가 종이 중심 설정에서 5mm 이상 떨어져 있으면 시작하지 않는다.
  - ±50mm 범위를 벗어나는 점이 하나라도 있으면 전송 전에 거부한다.
  - 사용자가 `yes`를 입력해야 시작한다.
- 명령마다 ok를 기다립니다. Alarm, limit, error 응답이나 타임아웃이 오면 즉시 멈추고 자동 복구를 하지 않습니다. 하트 테스트 때 받은 `Soft limit:B`가 이 경우에 해당합니다.
- 실행이 끝나면 결과, 걸린 시간, 설정 스냅샷을 `LOG/runs/run-*.json`에 저장합니다.

**검증.** 가짜 컨트롤러로 확인한 항목:
- 상태 문자열 파싱
- 정상 ACK를 받으면 끝까지 완료
- 4번째 명령에서 `Soft limit:B`가 오면 그 뒤 명령을 하나도 보내지 않음
- 응답이 없으면 타임아웃으로 멈춤
- 범위를 벗어난 점은 거부

`orientation-test-F.json`의 dry-run G-code도 눈으로 검토했습니다(11줄, 펜 동작 순서 정상).

**미검증.** 실물 로봇에서 실행해 본 적이 없습니다. 특히 `M20 G90 G01` 절대 좌표 형식과 명령마다 ok가 오는 동작은, 첫 실행 때 짧은 경로로 확인해야 합니다.

## 7. 좌우 부호 미검증 (작업 중 발견)

**정의.** 원과 하트는 좌우 대칭이라, 종이 오른쪽이 로봇 +Y인지 -Y인지 한 번도 드러나지 않았습니다. 사진을 그리면 좌우가 뒤집힐 수 있습니다.

**조치.** 로봇이 +X(벽) 방향을 바라보는 오른손 좌표계라고 가정하면, 종이 정면에서 본 오른쪽은 로봇 -Y입니다. 그래서 `paper_x_to_robot_y_sign = -1`로 두되 `unverified`로 표시했고, 실행기가 실행할 때마다 경고를 출력합니다. 좌우·상하가 모두 비대칭인 F자 시험 경로 `trajectories/orientation-test-F.json`(20×30mm)을 만들었습니다.

**확인 방법.** F를 그려 보고 다음과 같이 판단합니다.
- 종이 정면에서 F가 똑바로 보이면 설정 파일의 `_axis_sign_status`를 `verified`로 바꾼다.
- 거울상이면 Y 부호를 뒤집는다.
- 위아래가 뒤집혔으면 Z 부호를 뒤집는다.

## 8. rembg와 설계의 충돌

설계 3절은 "딥러닝 기반 의미 분할"을 첫 버전에서 제외한다고 했는데, CV 코드는 rembg를 기본으로 켜 두고 있었습니다. rembg는 기본값을 끄고 선택 전처리(`--rembg`, GUI 체크박스)로 두었으며, 필요할 때만 import합니다. 설계 문서 12절에 "경로 생성 핵심 단계에는 쓰지 않고 선택 옵션으로 허용"한다고 명시했습니다.

## 9~11. 코드 구조

- 공용 모듈은 `sketch_pipeline.py`와 `paper_mapping.py`입니다. GUI(`gui_sketch.py`)와 명령줄 도구(`make_strokes.py`)가 같은 함수를 씁니다. GUI를 실제로 띄워 처리 버튼 경로를 실행해 보니 CLI와 같은 결과(28획, 96점, 588mm)가 나왔습니다.
- GUI 변경 사항:
  - 선 후보(Canny/dark)와 추출 방법(skeleton/contour)을 고를 수 있다.
  - 그리기 크기 슬라이더를 추가했다.
  - 펜다운 길이, 펜업 거리, 예상 시간을 표시한다.
  - 그리는 순서 미리보기 칸을 추가했다.
  - 내보낸 파일이 곧바로 실행기 입력이 된다.
  - 슬라이더 값 표시가 드래그할 때만 갱신되던 문제를 고쳤다.
- 입력 이미지는 긴 변이 800px를 넘으면 줄입니다(`--max-side`). 최소 길이나 단순화 정도 같은 px 파라미터가 사진 해상도와 관계없이 비슷한 의미를 갖게 하기 위해서입니다.
