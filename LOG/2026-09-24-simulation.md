# 2026-09-24 — 3D 시뮬레이션으로 드로잉 경로 검증

F 시험 경로를 실물로 그리려 했지만, PC에 Mirobot(CH340, COM9)이 연결돼 있지 않았습니다. 확인된 포트는 COM5, COM6(블루투스)뿐입니다. 그래서 로봇 없이 경로를 검증할 3D 시뮬레이션을 먼저 만들었습니다. 이번 작업에서도 로봇은 움직이지 않았습니다.

## 만든 것

| 파일 | 역할 |
|---|---|
| `sim/mirobot_sim.py` | 실행기와 같은 G-code 경로를 1mm 간격으로 나눠 IK를 풀고 관절 한계를 검사. 관절 그래프, 3D GIF, 도달 지도, 관절 궤적 JSON 출력 |
| `sim/rviz_playback.py`, `sim/run_rviz.sh`, `sim/rviz/mirobot_sketch.rviz` | WSL2 ROS 2에서 공식 Mirobot URDF 3D 모델로 궤적 재생. A4 테두리와 펜다운 궤적 마커 표시 |
| `tests/test_sim.py` | 기구학·경로 테스트 6개 (전체 28개 통과) |

## 모델과 근거

- **관절 구조와 한계:** WLKATA 공식 ROS 2 저장소의 `wlkata_mirobot_description.urdf`(WSL `~/mirobot_ws`)에서 joint1~6의 origin, axis, limit를 옮겼습니다. 한계는 J1 −110°~160°, J2 −35°~70°, J3 −120°~60°, J4 −180°~145°, J5 −200°~30°, J6 ±360°입니다.
- **컨트롤러 좌표와의 대응:**
  - URDF의 link6 원점은 손목 중심이고, 홈 자세에서 (198.44, 0, 255.0)mm입니다.
  - 컨트롤러가 보고한 홈 TCP는 (198.668, 0, 230.477)입니다.
  - 차이는 플랜지 방향으로 24.52mm, 옆으로 0.23mm입니다. 0.23mm는 URDF 링크 길이 반올림(168.75mm)에서 생긴 차이로 봅니다.
  - 이 차이를 공구 오프셋으로 두면, 홈 자세에서 순기구학 결과가 컨트롤러 값과 1µm 이내로 일치합니다.
- **종이 중심 = 홈 자세:** `drawing_config.json`의 종이 중심 TCP가 홈 TCP와 같습니다. 즉 지금 설치에서는 호밍 직후 펜이 종이 중앙에 오도록 종이를 붙여 둔 상태입니다.
- **자세:** 명령 자세 A, B, C = 0은 홈 자세의 플랜지 방향과 같다고 가정하고, 그리는 동안 고정합니다.

### 도달 지도 (종이 평면, 자세 고정)

그림: `assets/2026-09-24-simulation/reach_map.png`

- 좌우 ±150mm와 아래쪽 −110mm까지는 여유가 충분합니다.
- 위쪽은 B(J5)가 30° 한계에 닿아 제한됩니다. 중앙 기준으로 **여유 5°가 약 +65mm, 한계가 약 +77mm**이고, 좌우 끝으로 갈수록 더 낮아집니다.
- 이전에 실물 하트를 그리다 받은 `Soft limit:B`(2026-09-23, 19번째 구간)와 같은 축입니다. 모델이 실물 동작과 일치한다는 근거로 볼 수 있지만, 그때의 정확한 경로가 남아 있지 않아 같은 지점이라고 입증되지는 않았습니다.
- 현재 실행기 범위(±50mm)는 안전합니다. 그림을 더 크게 그리려면 위쪽보다 아래쪽과 좌우로 넓히는 편이 유리합니다(예: 위 +50, 아래 −100, 좌우 ±120). 범위를 바꾸기 전에 해당 영역도 시뮬레이션하고 실물로 천천히 확인해야 합니다.

### 좌우 부호

팔 뒤쪽 시점(종이 정면과 같은 방향)으로 본 애니메이션에서 F가 정상 모양으로 그려졌습니다(`F_sim.gif`). 오른손 좌표계 가정(`paper_x_to_robot_y_sign = −1`)이 모델상으로는 맞다는 뜻입니다. 다만 실제 펌웨어의 Y축 방향은 실물 F 테스트로만 확인할 수 있으므로 `unverified` 상태를 유지합니다.

### 설치 기준 (사용자 확정)

A4 용지는 가로로 벽에 붙이고, 로봇을 켜서 호밍(영점)한 직후 **펜 끝이 종이 한가운데에 닿도록** 종이 위치를 맞춥니다. 실행기와 시뮬레이터의 기준인 "종이 중심 = 홈 TCP"가 이 규칙에서 나옵니다. `drawing_config.json`의 설명에도 적어 두었습니다.

### RViz 재생

`bash sim/run_rviz.sh out/F_traj.json 10`을 실행해 확인한 항목:
- robot_state_publisher가 link1~6을 인식함
- rviz2가 OpenGL 4.2로 시작함
- `/joint_states`에 joint1~6 값이 발행됨

창은 사용자 화면(WSLg)에 열립니다. 처음에는 창이 보이지 않았고, 아래와 같이 해결한 뒤 사용자가 화면에서 직접 확인했습니다.

### RViz 창이 보이지 않던 문제

**증상.** RViz는 실행되고 `/joint_states`도 발행됐지만, 사용자 화면에 창이 보이지 않았습니다. 작업표시줄에는 `[WARN:COPY MODE] ... - RViz (Ubuntu-22.04)` 창이 있었습니다.

**원인과 조치.**
1. `[WARN:COPY MODE]`는 WSLg가 공유 메모리 대신 복사 방식으로 창을 전달한다는 경고입니다. 이 상태에서 창이 투명하게, 즉 아무것도 그려지지 않은 채 떠 있었습니다. `wsl --shutdown`으로 WSLg를 다시 시작하자 경고가 사라지고 사용자 화면에 RViz가 보였습니다.
2. 재발에 대비해 `run_rviz.sh`는 기본적으로 소프트웨어 렌더링(`LIBGL_ALWAYS_SOFTWARE=1`)을 씁니다. GPU를 쓰려면 `MIROBOT_RVIZ_GPU=1`로 실행합니다.
3. Windows에서 Python으로 `run_rviz.sh`를 수정하면서 줄바꿈이 CRLF로 바뀌어, bash가 스크립트를 실행하지 못했습니다(`$'\r': command not found`). LF로 되돌리고 `.gitattributes`(`*.sh text eol=lf`)를 추가했습니다.

### 펜 끝 자국 표시

사용자 제안에 따라, 자국을 플랜지(TCP)가 아니라 **펜 끝**에 그리도록 바꿨습니다.
- 사용자 설명: 펜은 벽 쪽으로 수평, 플랜지에서 약 100mm.
- 이 값을 `drawing_config.json`의 `pen_tip_offset_mm = (100, 0, 0)`에 넣었습니다. 사용자 어림값입니다.
- 그리는 동안 자세가 고정이라 펜 끝은 항상 플랜지 + 같은 오프셋입니다. 이 값은 시각화에만 쓰고, 관절 계산과 실행기 명령에는 쓰지 않습니다.
- RViz: 펜홀더와 펜을 주황 막대로, 펜 끝을 구로 표시합니다. 펜다운이면 빨강, 펜업이면 회색입니다. 종이 테두리는 펜 끝 평면에 둡니다.
- GIF: 같은 방식으로 펜 막대를 그리고, 자국을 펜 끝에 표시합니다.

## 실행기 수정: 호밍 대기

**정의.** 설계 문서에 따르면 포트를 새로 열면 CH340이 보드를 리셋하고, 리셋 후에는 Alarm 상태로 시작합니다. 그런데 기존 실행기는 포트를 연 직후 Idle이 아니면 종료했습니다. 이대로면 `--execute`는 항상 실패합니다.

**해결.** `MirobotLink.wait_for_homing()`을 추가했습니다. Alarm이면 "중앙 버튼을 2초 눌러 호밍하세요"라고 안내하고, 최대 `idle_timeout_s`(180초) 동안 Idle이 되기를 기다립니다. 자동 호밍 명령은 보내지 않습니다. Idle이 되면 기존 검사를 그대로 거칩니다: 홈 TCP가 종이 중심에서 5mm 이내인지 확인하고, `yes` 입력을 받습니다.

**검증.** 가짜 컨트롤러로 Alarm → Alarm → Home → Idle 순서를 흉내 내어, 대기 후 Idle 상태와 TCP를 올바르게 받는지 확인했습니다.

## 한계

- 충돌(팔·펜홀더와 벽·종이)은 검사하지 않습니다. 펜 끝 오프셋(100mm)은 사용자 어림값이라, 그림 속 펜과 종이의 위치는 대략적인 것입니다. 실측하면 `pen_tip_offset_mm`를 고칩니다.
- 펌웨어의 실제 IK와 한계 처리는 URDF 모델과 세부가 다를 수 있습니다. 여유가 5° 미만인 경로는 실물에서 천천히 확인해야 합니다.
