## 새 문제 1: 만화 스크린톤 때문에 획이 수천 개

**정의.** 스크린톤의 망점이 Canny와 dark 모드에서 모두 작은 선으로 잡힙니다. 만화 1장에서 2000~2700획, 14~19분이 나왔습니다.

**시험한 전처리 (canny-low 기준):**

| 전처리 | 획 | 시간 |
|---|---|---|
| Gaussian 9px | 323 | 10.9분 |
| **미디언 7px** | **175** | **9.9분** |
| 미디언 9px | 136 | 8.9분 (세부 선이 더 사라짐) |
| bilateral | 2015 | 15.5분 (망점 남음) |
| 미디언 7px + closing + dark | 248 | 5.8분 (형태가 격자로 깨짐) |

**해결.** 미디언 블러는 작은 점 무늬를 지우면서 선의 경계는 남깁니다. `run_pipeline(median_ksize=...)`와 `make_strokes.py --median N` 옵션을 추가했습니다. 기본값은 0(사용 안 함)입니다.

**검증.** 단위 테스트를 추가했습니다. 지름 5px 망점 영역과 굵은 선을 함께 둔 합성 이미지에서, 미디언 7px을 쓰면 망점 획은 사라지고 선(150px 이상)은 남는지 확인합니다.

처음 만든 테스트는 망점이 너무 작아서, 미디언 없이도 Gaussian 블러만으로 사라졌습니다. 그래서 무엇을 검증하는지 분명하지 않았고, 망점 크기를 실제 만화에 가깝게 키웠습니다.

## 새 문제 2: 획이 많을 때 순서 계산이 매우 느림

**정의.** `order_strokes()`가 매 단계 남은 획 전체를 Python 반복문으로 훑는 O(n²) 구조였습니다. 만화 1장(2726획)에서 순서 계산에만 **80초**가 걸렸습니다. 같은 이미지에서 골격화는 5초, 추적은 0.8초, 단순화는 0.05초였습니다. 이미지 6장 비교가 10분 안에 끝나지 않은 원인입니다.

**해결.** 모든 획의 시작 후보점을 한 배열에 모았습니다(열린 획은 양 끝, 닫힌 획은 모든 꼭짓점). 매 단계 numpy로 한 번에 거리를 재도록 바꿨습니다.

**검증.**
- 무작위 획 300개(열린 획과 닫힌 획 섞음)에서 기존 구현과 **순서가 완전히 같음**을 확인했습니다.
- 2726획 기준 80초 → **0.85초**로 빨라졌습니다.

### 새 문제 3: 작은 원본 이미지는 디테일이 뭉개짐

**정의.** `load_gray()`는 긴 변이 800px보다 큰 이미지는 줄였지만, 작은 이미지는 그대로 두었습니다. 입력 원본 크기는 illust2 267×189px, illust1 447px, manga 532px입니다. 이런 작은 이미지에 같은 px 파라미터(최소 길이, 단순화 오차)를 적용하면 종이 위에서 상대적으로 더 거칠어집니다. 선도 계단 모양이 되고 눈·안경 같은 작은 형태가 사라졌습니다.

**해결.** `resize_max_side()`가 작은 이미지도 긴 변 800px로 키우도록 바꿨습니다(INTER_CUBIC, `upscale=True`가 기본). 이제 모든 입력이 같은 해상도 기준으로 처리됩니다.

**검증.**
- illust2(rembg + canny medium): 137획 → 429획. 안경, 눈, 손가락이 새로 나타났습니다.
- 단위 테스트 2개를 추가했습니다. 작은 이미지는 800px로 키우고, `upscale=False`면 그대로 두는지 확인합니다.

**부작용과 조치.** 만화를 1.5배 키우면서 스크린톤 망점도 커졌습니다. 그래서 미디언 7px로는 망점이 다시 남았습니다(668~1404획). 미디언 크기를 해상도에 맞게 다시 조정했습니다.

## 2026-09-25 — 그리기 범위 확대 준비 (±50 → ±60mm)

**배경.** 디테일이 늘어 100mm 안에 선이 촘촘해지면, 펜 굵기 때문에 실제 종이에서는 뭉개질 수 있습니다. 그래서 사용자가 안전 범위를 키워도 되는지 물었습니다.

**시뮬레이션 (정사각형 테두리):**

| 범위 | 판정 | 최소 여유 |
|---|---|---|
| ±50mm | PASS | B(J5) 11.6° |
| ±60mm | PASS | B(J5) 7.0° |
| ±70mm | WARN | B(J5) 1.2° |

**결정 (사용자 동의).** ±60mm는 가능하다고 봅니다. 그러나 근거가 시뮬레이션뿐이고 다음 세 가지가 확인되지 않았으므로, 바로 올리지 않고 실물 확인 절차를 거칩니다.
- 실제 펌웨어의 관절 한계
- 넓은 영역에서의 펜 접촉 불균일 (종이 평면 보정 안 됨)
- 팔·펜홀더와 벽의 충돌 (시뮬레이션에서 검사하지 않음)

**구현.**
- `drawing_config.json`:
  - `limits`는 ±50mm로 **유지**합니다.
  - `limits_pending_verification`(±60mm)에 상태 "시뮬레이션 PASS, 실물 미확인"을 기록하고, 확인 절차를 `_limits_pending_note`에 적었습니다.
  - ±70mm는 사용하지 말라고 적어 두었습니다.
- `draw_executor.py`:
  - `--pending-limits`: 이 옵션을 붙였을 때만 확장 범위로 검사하고, 매번 경고를 출력합니다.
  - `--air`: 펜다운 자세도 펜업 높이로 바꿔, 펜을 종이에 대지 않고 경로만 따라갑니다.
  - 실행 기록에 `air_mode`와 `pending_limits`를 함께 저장합니다.
- `trajectories/border-test-60mm.json`: ±60mm 테두리(120×120mm)를 한 획으로 그리는 경로입니다.

**검증.**
- 기본 실행은 테두리 경로를 거부합니다(종료 코드 2).
- `--air --pending-limits` dry-run에서는 9개 명령 모두 X=196.168입니다(접촉면 198.668에서 2.5mm 떨어짐).
- 시뮬레이션: PASS, B(J5) 여유 7.0°.
- 단위 테스트 3개를 추가해 전체 34개가 통과합니다.
  - 공중 모드에서 X가 접촉면에 닿지 않음
  - 확장 범위는 옵션을 붙였을 때만 적용되고 ±61mm는 거부됨
  - 테두리 파일이 두 범위 조건에 맞음

**실물 확인 순서.**
1. `python robot/draw_executor.py trajectories/orientation-test-F.json --execute`
2. `python robot/draw_executor.py trajectories/border-test-60mm.json --air --pending-limits --execute` — Soft limit과 충돌이 없는지 확인합니다.
3. `python robot/draw_executor.py trajectories/border-test-60mm.json --pending-limits --execute` — 네 변의 선이 고른지 확인합니다.
4. 문제가 없으면 `limits`를 60으로 올리고, 그림을 `--box 120 120`으로 다시 뽑습니다.
